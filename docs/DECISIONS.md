# DECISIONS — Fetchy

Формат: `D<n>: <решение> — <обоснование>`. Статус: приняты при планировании 2026-10-08.

- **D01: Kotlin/JVM + Compose Multiplatform Desktop, без Electron/Tauri.** Единый язык с логикой, нативная производительность, M3 Expressive доступен в CMP. Цена: упаковка через jpackage.
- **D02: Запуск процессов только через `ProcessBuilder(List<String>)`, без shell.** Снимает shell-инъекции из URL/аргументов, делает аргументы тривиально тестируемыми.
- **D03: Окружение процесса — UTF-8 (`file.encoding`, `LANG=C.UTF-8`, `LC_ALL=C.UTF-8`).** Иначе русские названия видео ломают вывод yt-dlp на Windows.
- **D04: `--ignore-config` в каждом вызове по умолчанию.** Изоляция от пользовательских yt-dlp-конфигов — предсказуемое поведение GUI; исключение только для явного режима «читать конфиг» из Settings (не в v1).
- **D05: Прогресс через `--newline` + собственный `--progress-template download:FETCHY|…`.** Стабильный машиночитаемый формат вместо парсинга человекочитаемого вывода; шаблон — контракт, зафиксирован в PLAN Global Constraints.
- **D06: Реестр опций — парсинг `yt-dlp --help` регэкспом `/^    (?:(-[\w-]), )?(--[\w-]+)(?:[ =](\S+))?[ \t]{2,}(.*)$/`.** ~280 опций без ручной поддержки; обновление yt-dlp обновляет и реестр.
- **D07: Список экстракторов — `yt-dlp --list-extractors` (1752 строки), лениво и с кэшем.** Не хранить в репозитории — брать у установленного бинарника.
- **D08: Классификация ошибок 9 классов (`NOT_FOUND`, `NETWORK`, `AUTH_REQUIRED`, `GEO_BLOCKED`, `DRM_PROTECTED`, `PLAYLIST_PARTIAL`, `NO_SPACE`, `FFMPEG_MISSING`, `BINARY_MISSING`, `UNKNOWN`) по stderr+exit code.** Единый язык ошибок для UI, логов и ретраев.
- **D09: Single-instance — ServerSocket в каталоге приложения (порт из lock-файла).** Второй запуск сигнализирует первому поднять окно и завершается; кросс-платформенно без нативных API.
- **D10: Лицензия MIT.** Простая, совместима с апстримами (yt-dlp — Unlicense, отдельный бинарник).
- **D11: yt-dlp и ffmpeg не бандлятся.** Лицензионная и весовая чистота; обнаружение/скачивание — `BinaryManager`/`ComponentsManager`, явное действие пользователя.
- **D12: Маскирование креденшалов в логах, отчётах и отображаемой команде (`CommandStringCodec`).** Пароли/cookies/URL-токены не должны попадать в UI-логи и скриншоты.
- **D13: Модульная структура `build-logic`/`designsystem`/`core:{model,ytdlp,data,platform}`/`feature:{add,queue,history,presets,settings,tools}`/`app`.** Компилируется по кусочкам, тесты изолированы, feature не знают друг о друге.
- **D14: Своя навигация на `sealed object Destination` + back-stack, без third-party nav.** Compose Desktop не требует фрагментной навигации; меньше зависимостей, анимации через motion-токены designsystem.
- **D15: DRM — сообщение «Это видео защищено DRM, yt-dlp не может его скачать» + кнопка «Показать лог»; никаких функций обхода.** Правка заказчика к §13 ТЗ: убран запрет с предупреждением для `--allow-unplayable-formats` в пользу класса ошибки `DRM_PROTECTED`; yt-dlp и сам отказывается от DRM.
- **D16: DI — Koin 4.2.2.** Лёгкий, JVM-дружелюбный, модульный (по модулю feature — свой Koin-модуль).
- **D17: Локализация — compose resources, EN/RU, с тестом паритета ключей и запретом hardcoded-строк.** Строка UI без перевода = падающий тест.
- **D18: Персистентность — SQLDelight 2.3.2.** Типобезопасный SQL, схема в репо, in-memory тесты на JDBC, лёгкий миграционный путь.
- **D19: Медиа-метаданные — `ffprobe` (JSON) через `ProbeParser` (kotlinx-serialization).** Единственный надёжный источник метаданных локального файла; ffprobe — тот же ffmpeg-пакет.
- **D20: CI — матрица `windows-latest`+`ubuntu-latest`, только сборка и тесты.** Страж регрессий кросс-платформенности без публикаций и без сети к сторонним сервисам.
- **D21: Целостность ffmpeg/deno — проверять файлы сумм выбранного источника, если они есть; при отсутствии помечать компонент «не проверен» с причиной в UI/логе.** Не пропускать проверку молча: у yt-dlp обязателен `SHA2-256SUMS`, у прочих — по факту наличия в источнике. Наличие/отсутствие сумм у конкретных источников фиксируется при реализации T2.2.
- **D22: Каналы yt-dlp — stable (`yt-dlp/yt-dlp`), nightly (`yt-dlp/yt-dlp-nightly-builds`), master (`yt-dlp/yt-dlp-master-builds`).** Имена ассетов по платформе (`yt-dlp.exe`, `yt-dlp_linux`, `yt-dlp_linux_aarch64` опц.) берутся из GitHub Releases API с fallback, без жёсткого хардкода.
- **D23: Политика обновлений — без автоустановки без согласия; автопроверка отключаемая; автоустановка yt-dlp опциональна и по умолчанию выключена.** Кэш «последней версии» на диске (TTL 6 ч) + ETag/`If-None-Match` (304 → кэш); ручная проверка обходит TTL, но не чаще 1 раза/мин; офлайн → тихо `OFFLINE`, без исключения в UI.
- **D24: Установка — атомарная замена (`ATOMIC_MOVE` с fallback), один `.bak` с откатом при провале пост-проверки, `chmod +x` на Linux.** Windows: запущенный `.exe` перезаписать нельзя → `UPDATE_BLOCKED_BY_ACTIVE_TASKS` при активных задачах. Синхронизация: `Mutex` на компонент + объединение конкурентных запросов на установку в один (single-flight).
- **D25: Загрузка — только HTTPS, редиректы <= 5 с запретом понижения до HTTP, temp `*.part` в целевом каталоге, возобновление через `Range` при поддержке (иначе заново), `Flow<DownloadProgress>`.** Отмена корутины сохраняет `.part` для докачки. Таймауты connect/socket/общий и 3 повтора с экспоненциальной паузой. Прокси — из настроек (отдельная опция для загрузки компонентов). HTTP-слой за интерфейсом `ComponentDownloader` (тесты на Ktor MockEngine).
- **D26: Размер уже скачанного `.part` пересчитывается на каждой попытке загрузки, а не один раз.** До правки `existingSize` вычислялся до цикла повторов и переиспользовался: при обрыве соединения уже дописанные байты снова добавлялись к `Range`, что давало дублирование и порчу файла. Теперь размер читается заново в начале каждой попытки; `200` при непустом `.part` (сервер проигнорировал `Range`) перезаписывает файл с нуля.
- **D27: Ответ `416 Range Not Satisfiable` на непустой `.part` трактуется как «возобновление невозможно»: `deleteIfExists(part)` и ровно один перезапуск с нуля (`Step.Restart`).** Повторный `416` после перезапуска уже летит как ошибка — иначе возможен бесконечный цикл. Лимит редиректов проверяется в обеих точках (`download`/`get`) и покрыт тестом.
- **D28: `CancellationException` никогда не проглатывается.** В `AtomicInstaller.install` отмена во время пост-проверки делает откат из `.bak` и пробрасывает исключение дальше; в `ComponentsManager.verify` — немедленный rethrow. `DefaultProcessLauncher.run` в `finally` добивает процесс (`destroyForcibly`), чтобы не оставлять «осиротевшие» процессы при отмене/таймауте.
- **D29: Защита от выхода за пределы каталога распаковки покрывает не только обычные записи, но и символические/жёсткие ссылки tar.** Перед `tar -xf` выполняется `tar -tvf` и проверка первой колонки типа: любой `l`/`h` (или наличие ` -> `) → `ComponentError.UnsafeArchiveEntry`. Наши архивы (ffmpeg/deno) link-записей не содержат, поэтому они отвергаются целиком.
- **D30: `ArgvBuilder` строит argv из типизированной модели (`YtDlpInvocation`/`YtDlpOptions`) в детерминированном порядке групп; `--ignore-config` добавляется всегда, кроме явного `readUserConfig = true`.** GUI-владеемые опции (`--ignore-config`, `--newline`, `--progress-template`, `--progress`/`--no-progress`) нельзя переопределить из пользовательских «Все опции»/raw-args: они отбрасываются с предупреждением в `BuiltCommand.warnings`. URL добавляются последними; если URL начинается с `-`, перед ними вставляется разделитель `--`.
- **D31: Маскирование креденшалов — единая точка в `CommandStringCodec.mask`, применяется к отображаемой команде и логам (Global Constraint 5).** `ArgvBuilder` возвращает и реальный `argv`, и `maskedArgv` (через `mask`). Маскируются значения `--password`/`-p`, `--video-password`, `--twofactor`, `--ap-username`, `--ap-password`, `--cookies` (в формах `--opt value` и `--opt=value`), userinfo в `--proxy` и URL (`user:pass@`), а также секретные HTTP-заголовки в `--add-headers` (`Authorization`, `Cookie`, `X-Api-Key` и т.п.).
- **D32: `CommandStringCodec` форматирует и разбирает командные строки без выполнения и раскрытия shell-семантики (`$VAR`, `%VAR%`, глобы остаются литералами).** Поддержаны BASH, CMD (list2cmdline-совместимое экранирование), POWERSHELL (одинарные кавычки с удвоением). Гарантируется round-trip `parse(format(argv)) == argv` для пробелов, кавычек, пустых аргументов, юникода и Windows-путей. `importArgs` распознаёт и отбрасывает ведущий `yt-dlp`/`yt-dlp.exe` (в т.ч. с путём).
- **D33: `HelpParser` толерантен к неизвестному формату (не падает, пропускает лишнее) и разбирает реальный `yt-dlp --help` в реестр опций (секция, длинная/короткая форма, метавар, многострочное описание, альтернативные имена, раскрытие `--[no-]flag` в обе стороны).** Реестр сериализуется вручную через `kotlinx.serialization.json`-дерево (без плагина) и кэшируется на диск по версии (`HelpRegistryCache`). Golden-фикстура `fixtures/ytdlp-help.txt` — реальный вывод `yt-dlp 2026.08.19` (255 опций). Уточнение: секция называется `Network Options` (в PLAN ошибочно «Networking Options»).
- **D34: диагностическая модель `MediaInfo`/`MediaStream` живёт в домене (`fetchy.model`), а не в `core/ytdlp`; `ProbeParser` (core/ytdlp) только наполняет её.** T2.1 в PLAN-списке моделей `MediaInfo` пропустил (пробел плана); при T2.4 он добавлен рядом с `ProgressInfo`, чтобы feature-слой (Tools) потреблял его без зависимости от внутренностей `core/ytdlp`. Дубликат `HelpOption` (`fetchy.model` из T2.1 ↔ `fetchy.ytdlp` из T2.3) зафиксирован и подлежит сверке/слиянию при T6.2/T7 (один тип-владелец реестра).
- **D35: `ProbeParser` разбирает JSON `ffprobe` вручную через `kotlinx.serialization.json`-дерево (без плагина сериализации), толерантно:** отсутствующие поля → `null`, `MediaStream.index` дефолт `0`, `type` = `codec_type` (иначе `"unknown"`), `avg_frame_rate` в формате `num/den` → `Double` (деление на ноль → `null`). `MediaInfo` даёт помощники `videoStream`/`audioStream`/`hasVideo`/`hasAudio`; `format.tags.title` → `title`. Зависимость `kotlinx-serialization-json` уже подключена в T2.2 — правка TOML не требуется.
- **D36: `YtdlpProcessRunner` стримит процесс через `channelFlow`: stdout и stderr читаются конкурентно; строки с префиксом `download:FETCHY|` маршрутизируются в `ProgressEvent.Progress` (разбор `ProgressParser`), прочий stdout → `Stdout`, stderr одновременно копится в буфер и отдаётся как `Stderr`.** По завершении: код `0` → `Completed(0)`, иначе → `Failed(YtdlpError)`, где `errorClass = ErrorClassifier.classify(stderr, exitCode)`, `message` = последняя непустая строка stderr, `rawStderr` целиком. Env принудительно UTF-8 (`LANG`/`LC_ALL`/`PYTHONIOENCODING`), `redirectErrorStream=false`, всегда `ProcessBuilder(List<String>)`, без shell. Ошибка старта процесса → `ProcessStartException`.
- **D37: отмена раннера уничтожает процесс немедленно (`destroy` → ожидание `terminateGraceMillis` → `destroyForcibly`), не дожидаясь естественного завершения.** Ожидание кода возврата сделано на `process.onExit()` через `suspendCancellableCoroutine`, а `invokeOnCancellation` вызывает `terminate`; это делает отмену отзывчивой (снятие корутины не ждёт `waitFor`), тогда как `finally`-`terminate` идемпотентен. Это реализация Global Constraint (отмена убивает процесс) и D28 применительно к длительным загрузкам.
- **D38: `YtdlpProcessRunner` отдаёт «хвост» терминальным событием (`Completed`/`Failed`) и не бросает исключение на ненулевой код — вызывающий решает политику.** Это сохраняет `Flow` тотальным и тестируемым; `CancellationException` при отмене пробрасывается как обычно (не глотается).
- **D39: персистентность — SQLDelight 2.3.2 (JVM/JDBC), плагин `app.cash.sqldelight` + `create("FetchyDatabase") { packageName = "fetchy.data.db" }`; схема — 4 таблицы (`download`, `history`, `preset`, `setting`) в `src/main/sqldelight/fetchy/data/db/*.sq`.** Проверено: SQLDelight 2.3.2 работает на Gradle 9.8.0 (генерация + `verifyMainFetchyDatabaseMigration` зелёные). Плейсхолдер `fetchy.core.data.Data` удалён; код в пакете `fetchy.data`.
- **D40: enum-поля (`TaskStatus`, `ErrorClass`) хранятся как TEXT (`.name`) и маппятся в репозиториях, а НЕ через `ColumnAdapter`.** Это держит сгенерированный API примитивным (без adapter-параметров конструктора `FetchyDatabase`) и изолирует маппинг в одном слое; `ErrorClass` — nullable.
- **D41: репозитории отдают реактивные потоки через `Query.asFlow().mapToList(dispatcher)` (coroutines-extensions), где `dispatcher: CoroutineContext = Dispatchers.IO` инъектируется в конструктор; точечные чтения — `executeAsOne()/executeAsOneOrNull()` (члены `ExecutableQuery`) через `withContext(dispatcher)`.** 4 репозитория: `DownloadRepository` (observeAll/observeActive/get/create/updateStatus/updateProgress/delete/activeCount), `HistoryRepository` (observeAll/search/get/insert/delete/deleteAll/count), `PresetRepository` (observeAll/get/create/update/delete), `SettingsRepository` (observeAll/get/put/remove). Доступ к БД — `FetchyDatabaseFactory.create(driver)` и `inMemory()` (`JdbcSqliteDriver.IN_MEMORY` + `Schema.create`).
- **D42: в таблице `setting` ключ назван `setting_key` (не `key`), а SQLDelight переименовывает колонку `value` в сгенерированное `value_`.** Имена выбраны, чтобы избежать коллизий со служебными/ключевыми именами SQLite и Kotlin и не ломать генерацию. Известный минор: плагин SQLDelight провоцирует предупреждение KGP «Kotlin plugin loaded multiple times» (app/core:data) — сборка зелёная, проверено.
- **D43: файловые пути приложения — `core/platform/AppDirs.resolve()` + `AppPaths` (Windows `%LOCALAPPDATA%\Fetchy` с фолбэком `%APPDATA%`, macOS `~/Library/Application Support/Fetchy`, Linux `$XDG_DATA_HOME/fetchy` иначе `~/.local/share/fetchy`); `AppPaths` даёт `config/cache/logs/data`, `data/fetchy.db`, `fetchy.port` и `ensureExists()`.** Пути инъектируются через Koin (`single { paths }`) — тестируемость и отсутствие глобального состояния.
- **D44: single-instance — port-file протокол в `core/platform/SingleInstance` (не lock-файл).** Первичный инстанс биндит `ServerSocket(0, 50, loopback)`, пишет порт в `fetchy.port` и держит daemon-thread accept-loop; вторичный читает порт, шлёт строку `FETCHY_FOCUS` (протокол: `readLine()` съедает `\n`, поэтому константа без перевода строки, а запись добавляет `\n`) и завершается (exit 0); первичный по приёму вызывает `onFocusRequested` → `toFront()`/`requestFocus()`. `close()` закрывает сокет, join-ит поток и удаляет port-file. Известный дефект (deferred): если port-file устарел и указывает на живой чужой порт, вторичный ложно сигналит и тихо выходит — нужна ack-проверка пира (отложено в review).
- **D45: Compose-ресурсы (`composeResources`) включены для всех Compose-модулей в `build-logic/fetchy.compose.gradle.kts`: прямой артефакт `org.jetbrains.compose.components:components-resources` + `compose.resources { generateResClass = ResourceClassGeneration.Always }`.** Accessor `compose.components.resources` в Compose MP 1.12.0 deprecated, поэтому используем прямой модуль; сгенерированные `Res`/строковые accessor-ы `internal` и живут в `<group>.<module>.generated.resources` (для app — `fetchy.app.generated.resources`). Строки EN/RU — в `app/src/main/composeResources/values{,-ru}/strings.xml`, parity покрыт тестом.
- **D46: app-граф — `AppGraph` (Koin) поверх `koinApplication { modules(...) }` (изолированный контекст без глобального `GlobalContext`), c `Koin`-фасадом; `single<SqlDriver>(createdAtStart = true)` создаёт драйвер и БД-схему на старте, `onClose { it?.close() }` (import `org.koin.dsl.onClose`) закрывает драйвер.** Это закрывает medium M1 из review T3.1 (драйвер ранее не закрывался). `AppGraph.close()` идемпотентен (`runCatching`). В Koin 4.2.2 `koinApplication` живёт в `org.koin.dsl` (не `org.koin.core.context`, как в Koin 3) — частая ловушка компиляции.
- **D47: навигация — собственный `FetchyNavController` (back-stack на `SnapshotStateList`) + `Destination` sealed interface (`Add/Queue/History/Presets/Settings/Tools/Gallery` data objects, `Detail(id)`), без third-party nav (PLAN/D14).** `topLevel(dest)` очищает стек до одного элемента (клики по NavRail); `pop/popTo/replace` — конкретные операции; переходы — `NavigationTransition.FadeThrough` из designsystem. NavRail с иконками (`Icons.AutoMirrored.Filled.List` вместо deprecated `Icons.Filled.List`).
- **D48: жизненный цикл окна — `Main.kt` делает single-instance check до создания окна, `AppGraph.start` до `application {}`, а очистку (граф + single-instance) выполняет в `onCloseRequest` ПЕРЕД `exitApplication()`.** Важно: Compose Desktop `exitApplication()` вызывает `exitProcess`, который НЕ выполняет `finally`-блоки, поэтому cleanup продублирован явно; `finally` остаётся страховкой для нормального возврата `application {}`. Окно: 1100×720 начальный размер, минимум 1100×720 через `(window as? Frame)?.minimumSize`. `compose.desktop.application.mainClass = "fetchy.app.MainKt"`.
- **D49: single-instance claim — атомарное получение primary через `Files.write(portFile, port, CREATE_NEW, WRITE)` (маркер владения и содержимое порта в одной атомарной записи), а не «проверить и записать».** Закрывает TOCTOU-гонку (M3 review T3.2): при `FileAlreadyExistsException` инстанс повторно пытается просигналить живой primary (тогда он вторичный) либо удаляет устаревший файл и повторяет попытку (bounded `MAX_CLAIM_ATTEMPTS = 5`). Чужой/живой claim никогда не удаляется.
